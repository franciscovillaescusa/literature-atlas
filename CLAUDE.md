# Literature Atlases — notes for Claude

One codebase builds an atlas per project (currently `camels`, `quijote` and `fvillaescusa`, a person's publications from an arXiv author search: see the optional settings in the `Project` docstring of `build_atlas.py`). Each project has
`projects/<name>/` (`config.json`, `tags.json`, `overrides.json`, `positions.json`) and a generated site
`<name>/index.html` (plus `<name>/preview.png`), built by `build_atlas.py --project <name>` from `atlas.html`,
`atlas.css`, `atlas.js` and the data files. Never edit `<name>/index.html` by hand. The root `index.html` is the
landing page, generated by `build_index.py` (the update job runs it). A GitHub job rebuilds every project on the 1st and 15th of each month and opens an
issue titled "New papers need tags (<Name>)" when a project has untagged papers.

Use the project's virtual environment if there is one (`.venv/bin/python`), otherwise `python3`.

## Tagging new papers ("tag the new <name> papers")

If the user does not say which project, check the open "New papers need tags (...)" issues (`gh issue list`)
or run step 3 for every project.

1. `git pull` (the job may have pushed new papers).
2. `python3 build_atlas.py --project <name> --offline` (refreshes the site from the cache if needed; if
   `atlas_cache/<name>/` is missing, run without `--offline`).
3. `python3 tagging.py <name> list` — shows each untagged paper (title, abstract) and the allowed tag names.
   If it lists **possibly renamed** papers (an already-tagged paper whose title or link changed on the
   publications page), confirm with the user, then add the suggested `{"id": ...}` line to
   `projects/<name>/overrides.json` and rebuild instead of tagging the paper again.
4. Read each abstract and add an entry to `projects/<name>/tags.json`, keyed by the paper ID:
   `{"title": ..., "suite": [...], "data": [...], "method": [...], "uncertain": [...]}`.
   Use only the allowed names (`tag_axes` in the project's `config.json`). Put a tag in `"uncertain"` when the
   abstract does not state it clearly. For papers without an abstract, tag from the title, mark all tags
   uncertain and add `"note": "No abstract available: tags guessed from the title only; please check."`.
   Conventions (`tag_conventions` in `config.json`): the "not stated" suite name when no suite or simulation
   set is named; the "other simulations" name when other simulations are also used; "No ML" for papers
   without machine learning.
5. `python3 tagging.py <name> unassigned` — if a paper in "Unassigned (new papers)" clearly fits a topic,
   propose it to the user and, if they agree, add `{"topic": "<exact topic name>"}` for it to
   `projects/<name>/overrides.json`.
6. Rebuild and test:
   `python3 build_atlas.py --project <name> --offline && python3 validate_atlas.py --project <name> && python3 check_atlas.py --project <name> --chrome`
   (`check_atlas.py` needs `pip install playwright`).
7. Show the user the tags you assigned, then commit (`projects/<name>/` — tags, overrides, positions,
   s2_matches — plus `<name>/index.html` and `<name>/preview.png`) and push.
8. Close the open issue: `gh issue close <number> -c "Tagged in <commit>"`.

## Setting up a new project

1. Create `projects/<name>/config.json` from an existing one (placeholder `topics` "Topic 1"... with empty
   `probes`, `topic_seed` `{}`, the project's own `tag_axes`, `tag_conventions` and `check`), and `tags.json`
   / `overrides.json` containing `{}`.
2. `python3 build_atlas.py --project <name>` — with an empty `topic_seed` it clusters from scratch.
3. `python3 tagging.py <name> topics` — read every cluster's titles, propose names (and short names) to the
   user, then write them into `topics` and fill `topic_seed` with every paper's ID -> its topic index from the
   built data, so the names stay attached to their papers.
4. Tag every paper (above), rebuild, run both checks, run `python3 build_index.py` (the landing page gets a
   card from the config's `description`), commit.

## Other notes

- Hand corrections go in `projects/<name>/overrides.json`, not in code. Topics of existing papers are fixed in
  `topic_seed`; `--recluster` would redo them and needs topic names reviewed.
- Layout positions are stored in `projects/<name>/positions.json` so the maps stay stable; commit it with the site.
- The ADS token is read from `~/.ads/dev_key` locally and from the `ADS_TOKEN` secret in GitHub.
- Changes to `atlas.js`, `atlas.html`, `atlas.css` or `build_atlas.py` affect every project: run the unit tests
  (`python3 -m pytest -q`), then rebuild and check all projects (`for p in $(ls projects); do ...; done`).
  When you fix a bug, add a test in `tests/` that fails without the fix.
